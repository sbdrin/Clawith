# 日志系统架构

该应用使用 **loguru** 作为主要的日志框架，并结合自定义中间件实现了结构化日志记录和分布式追踪功能。

## 核心框架与工具

- **主日志框架**: loguru (版本 >= 0.7.0)
- **标准库日志重定向**: 通过拦截器将标准库 logging 输出重定向到 loguru
- **分布式追踪**: 基于 ContextVar 实现的 trace_id 传播机制

## 关键文件与组件

### 1. `backend/app/core/logging_config.py`
这是整个日志系统的配置中心，负责:
- 初始化 loguru 并配置输出格式
- 设置包含 trace_id 的日志格式 `<green>{time:YYYY-MM-DD HH:mm:ss}</green> | <level>{level}</level> | <cyan>{extra[trace_id]:-<12}</cyan> | <cyan>{name}</cyan>:<cyan>{line}</cyan> - <level>{message}</level>`
- 提供 trace_id 的生成、获取和设置功能
- 定义并静默一些噪音较大的连接日志（如 uvicorn.access, websockets 等）
- 实现标准库日志拦截器，确保第三方库日志也通过 loguru 输出

### 2. `backend/app/core/middleware.py`
包含 `TraceIdMiddleware` 中间件，负责:
- 在 HTTP 请求中注入和传播 trace_id
- 记录请求进入和响应完成的日志
- 将 trace_id 添加到响应头中

### 3. `backend/app/main.py`
在应用启动时调用日志配置函数，确保日志系统在所有服务启动前就绪。

## 架构与约定

### 日志级别
- 默认级别为 INFO
- 支持标准日志级别 (DEBUG, INFO, WARNING, ERROR, CRITICAL)
- 特定噪音日志被提升到 WARNING 或 ERROR 级别以减少干扰

### 结构化日志
- 所有日志都包含时间戳、日志级别、trace_id、模块名和行号
- trace_id 用于关联同一请求链路中的所有日志
- 支持结构化数据记录（通过 extra 字段等）

### 分布式追踪
- 使用 ContextVar 实现异步上下文中的 trace_id 传播
- HTTP 请求通过 X-Trace-Id 头传递 trace_id
- 后台任务通过 `new_trace_id()` 生成独立的追踪ID

## 约定与约束

### 日志使用约定
- 应用代码中普遍使用 `from loguru import logger` 导入
- 在各个 API 模块和服务模块中直接使用 logger 记录信息
- 错误日志通常包含足够的上下文信息以便调试

### 日志输出格式
- 标准输出格式包含时间、级别、trace_id、源文件位置和消息内容
- trace_id 固定为 12 位字符宽度，不足部分用 `-` 填充

### 第三方库日志处理
- 通过拦截器机制将标准库 logging 输出重定向到 loguru
- 静默特定的噪音日志（如连接层日志）
- 确保所有日志输出的一致性

### 特殊日志类型
除了常规的应用日志外，系统还实现了专门的活动日志和审计日志：
- **活动日志** (`app/services/activity_logger.py`): 专门记录智能体行为，存储到数据库
- **审计日志** (`app/services/audit_logger.py`): 记录安全相关事件，如登录、权限变更等

这些特殊日志类型虽然使用 logger 记录错误，但主要数据是通过数据库表进行持久化的。
