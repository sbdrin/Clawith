## 简介
本文件面向所有希望参与 Clawith 项目的贡献者，系统化说明贡献流程与协作规范，包括：
- Git 工作流与分支策略
- 提交信息与 PR 规范
- Issue 报告模板与功能请求格式
- Pull Request 审查与合并标准
- CI/CD 流水线、自动化测试与发布流程
- 社区参与与讨论规范

Clawith 是一个开源的多智能体协作平台，采用前后端分离架构（前端 React + TypeScript，后端 FastAPI），通过 Docker 编排运行。贡献方式涵盖 Bug 修复、新功能、MCP 集成、翻译、文档与测试等。

## 架构总览
下图展示从贡献到发布的端到端流程：开发者在本地完成修改并推送至远端，触发 CI/CD 进行构建与测试，随后通过 Release 工作流生成版本与发布说明，最终发布到 GitHub Releases 或私有服务器。

```mermaid
sequenceDiagram

participant GH as "GitHub"
participant Drone as "Drone CI"
participant Actions as "GitHub Actions"
participant Server as "生产/测试服务器"
Dev->>GH : 推送代码 / 打开 PR
GH-->>Drone : 触发 CI (push/PR/tag)
Drone->>Drone : 构建镜像(旧版+新版)
Drone->>Drone : 空库迁移测试
Drone->>Drone : 全新部署测试
Drone->>Drone : 升级测试(旧→新)
alt 触发 release 工作流
Actions->>Actions : 计算版本号/生成发布说明
Actions->>GH : 创建 release PR
GH-->>Actions : PR 合并
Actions->>GH : 打 tag 并发布 Release
end
alt 仅 tag 事件
Drone->>Server : 导出镜像并部署
Drone->>Server : 重启服务与健康检查
Drone-->>Dev : 通知成功/失败
end
```

## 详细组件分析

### Git 工作流与分支策略
- 推荐从 main 拉取最新代码，为每个特性新建独立分支
- 保持 PR 聚焦单一特性或修复，便于审查与合并
- 若同一分支包含多个逻辑变更，建议使用交互式暂存（git add -p）拆分为多个提交与 PR

```mermaid
flowchart TD
Start(["开始"]) --> CheckoutMain["从 main 拉取最新代码"]
CheckoutMain --> CreateBranch["为特性创建新分支"]
CreateBranch --> Develop["开发与提交(频繁小提交)"]
Develop --> Split{"是否混合了多个特性?"}
Split -- 是 --> UsePatch["使用 git add -p 拆分提交"]
Split -- 否 --> Push["推送分支并创建 PR"]
UsePatch --> Push
Push --> Review["代码审查与迭代"]
Review --> Merge["合并到 main"]
Merge --> End(["结束"])
```

### 提交信息规范
- 建议遵循语义化提交（如 feat、fix、chore 等），并在 PR 描述中使用 Fixes #<issue_number> 关联问题
- 提交信息应清晰描述变更目的与影响范围

### Pull Request 流程与审查要求
- 先创建或关联 Issue，再提交 PR
- PR 需包含摘要与相关 Issue 链接
- 本地测试通过后提交，确保无无关变更
- 代码风格：后端使用 ruff；前端遵循 React 约定
- 合并标准：通过 CI 检查、至少一次审查、无阻塞错误

```mermaid
sequenceDiagram
participant Dev as "开发者"
participant GH as "GitHub"
participant CI as "CI/CD"
participant Reviewer as "审查者"
Dev->>GH : 创建 PR(含摘要与Issue链接)
GH-->>CI : 触发 CI 检查
CI-->>GH : 返回检查结果(构建/测试/迁移/部署)
Reviewer->>GH : 审查与评论
Dev->>GH : 根据反馈修改并提交
CI-->>GH : 再次检查通过
Reviewer->>GH : 批准合并
GH-->>Dev : PR 合并到 main
```

### CI/CD 流水线与自动化测试
- 使用 Drone CI 执行构建、迁移测试、部署测试与升级测试
- 使用 GitHub Actions 执行 Release 流程（版本计算、AI 生成发布说明、打 Tag 与发布）
- 测试覆盖：空数据库迁移、全新部署、从旧版本升级到新版本

```mermaid
flowchart TD
Trigger["触发事件(push/PR/tag)"] --> Build["构建镜像(旧版+新版)"]
Build --> MigrationTest["空库迁移测试"]
MigrationTest --> DeployTest["全新部署测试"]
DeployTest --> UpgradeTest["升级测试(旧→新)"]
UpgradeTest --> Success{"全部通过?"}
Success -- 否 --> NotifyFail["通知失败(飞书)"]
Success -- 是 --> TagEvent{"是否为tag事件?"}
TagEvent -- 否 --> End["结束"]
TagEvent -- 是 --> SaveImages["保存镜像并上传服务器"]
SaveImages --> Restart["重启服务与健康检查"]
Restart --> NotifySuccess["通知成功(飞书)"]
NotifySuccess --> End
```

### 发布流程（Release）
- 手动触发或通过 PR 合并自动触发
- 自动计算下一个版本号（patch/minor/major）
- 使用 GitHub Models 生成发布说明（可回退到基于提交信息的自动生成）
- 创建 release PR，合并后打 Tag 并发布 GitHub Release

```mermaid
sequenceDiagram
participant User as "用户"
participant Actions as "GitHub Actions"
participant GH as "GitHub"
User->>Actions : 触发 release workflow(指定类型/预发布/AI生成)
Actions->>Actions : 解析基础标签与目标版本
Actions->>Actions : 收集提交历史与生成提示词
alt AI可用
Actions->>GH : 调用 GitHub Models 生成发布说明
else AI不可用
Actions->>Actions : 基于提交信息生成发布说明
end
Actions->>Actions : 更新版本文件
Actions->>GH : 创建 release PR
GH-->>Actions : PR 合并
Actions->>GH : 打 Tag 并发布 Release
```

## 故障排查指南
- 常见问题：Windows 编码、代理拦截 LLM API、uvicorn 重载崩溃、路径反斜杠
- 调试建议：查看 CI 日志、保留诊断输出、检查环境变量与网络配置
- 发布失败：检查镜像标签、服务器配置文件、健康检查超时
